## What 2.4 has achieved and what remains

The branch's release record and CI show substantial implementation and validation:
Python 3.10–3.13, frontend browser journeys, three-platform installation, docs and
packaging pass. MATLAB Linux R2026a is green (511 pass, 12 Coder tests skipped);
Windows is experimental and has 36 skips. The reported local development run has
523 MATLAB tests passing with Coder/Simulink installed. These local MATLAB counts
are the branch author's recorded evidence, not a fresh MATLAB run in this audit.

Outstanding release decisions and limits:

1. **Version alignment:** MATLAB identifies as 2.4.0; Python/frontend remain 2.3.1.
   No 2.4 tag/package publication has occurred. Coordinate a release PR after the
   dependency backlog is resolved.
2. **LTE scientific status:** the registered run has 102/115 items within budget,
   seven outside and six unevaluable at +350 Hz. The seven ACLR misses reach
   0.21 dB against a 0.1 dB budget. Do not mark the LTE profile cross-validated or
   relax thresholds to clear a review gate. #80 records this honestly.
3. **Apply semantics:** SDK/MATLAB `auto` streams `gru`/`gmp`, while stored Studio
   scores use `offline_segmented`. The preregistered study supports that decision,
   but reproducing historical scores requires the explicit segmented option.
   Promoting experimental streaming models and offering the option in Studio are
   separate decisions; approval of this PR does not silently make either change.
4. **MATLAB coverage:** R2024b is a candidate minimum, not a verified minimum.
   macOS/other releases, Coder on hosted CI and embedded generated-code targets
   remain unverified. Windows's green experimental job is not a required gate.
5. **Instruments:** the lab session is mock-tested; no real instrument adapter
   ships. A software review cannot replace bench validation and RF-off interlocks.
6. **Reproducibility:** the release record describes mutation/fuzz testing but
   says its throwaway harness is absent. Treat those counts as reported evidence;
   retain a reproducible harness if it is to become a continuing release criterion.
7. **MATLAB gate:** the live main ruleset requires only the existing 13 CI checks;
   it does not yet require the new MATLAB Linux job. Its path-filtered workflow
   needs a suitable required-check design before it can be advertised as an
   enforced release gate for all relevant MATLAB/runtime changes.

## Previous rules versus actual enforcement

The old documentation and backbone gate require an independent **human**
admin/maintainer approval of the exact head. Bot accounts, the PR author's account
and comments are rejected. CODEOWNERS broadly covers Python, frontend, scripts,
workflows and scientific paths. Scientific work also calls for a separate PR and
`science-review-approved`; a label is not sufficient for the executable gate.

The live [ruleset 24579567](https://github.com/lab-emi/OpenDPD/rules/24579567)
actually requires only 13 GitHub Actions checks with strict up-to-date checking
and no bypass actors. There is no classic main branch protection, no required PR
approval rule, and neither existing review gate is a required status. Thus
CODEOWNERS and red advisory jobs do not by themselves enforce the written rule.
All three GitHub merge methods are enabled; auto-merge is disabled. Contributor
and reviewer commit trailers were not required by the written contribution guide.

The [updated policy](../architecture/review-policy.md) permits independent agents,
including explicit attestations for separate agents sharing an authorized GitHub
account, requires review on all PRs, preserves scientific/CI gates and prescribes
attributed merge commits. Deploy its trusted implementation before applying its
additional no-bypass ruleset. Changing review policy does not approve the six
pending PRs or publish 2.4.
