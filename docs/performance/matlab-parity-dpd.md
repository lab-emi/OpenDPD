# OpenDPD ↔ MATLAB parity: the memory-polynomial DPD

Status: **pre-registered; run 1 done — the memory-polynomial parity passes as registered** (2026-10-09). The registration (rules, data, MathWorks configuration, budgets
and the scored/diagnostic split) is committed before any comparison script exists or is run. The commits that
follow change only this status line, the run log and the Results section; they do not edit the registration. If
the registration itself must change, that is a dated amendment appended below, never an edit in place.

MATLAB users already trust `comm.DPDCoefficientEstimator` and `comm.DPD`. OpenDPD's `mp_ls` is the same model
class (memory polynomial, least squares, indirect learning). If the two agree up to the listed conventions, then
OpenDPD's baseline can be checked by anyone who has those functions, and a model fitted in OpenDPD (for example
on measured data in Studio) can be run by `comm.DPD`, which is what the planned `opendpd-model-v1` export relies
on. This document fixes **what is compared, with which MathWorks functions and which budgets, before any number
exists**, and records the outcome afterwards, including everything that does not agree.

## Rules

1. Data, MathWorks configuration and budgets below are fixed before the first run. A run never changes them.
2. The budgets are numerical-agreement budgets for two implementations of the same least-squares problem. They
   are loose compared with double-precision round-off (so that conditioning does not decide the verdict) and
   tight compared with any convention difference, which would produce differences of order one: **1·10⁻⁶**
   relative where conditioning or a single-precision interface is involved, **1·10⁻⁹** for double against
   double where neither is. They are not tuned on results.
3. An item passes if its measured difference is within its budget. An item outside its budget is reported as
   failed with the numbers; the explanation is a hypothesis until it is shown (a diagnostic run is allowed and
   is reported next to the failure, never instead of it).
4. If a comparison disagrees because the **MATLAB-side code does not implement the registered procedure** (a
   bug in the check, not a difference between the two tools), the MATLAB code is corrected to the registered
   procedure and the run is repeated. Every run, including the ones discarded, appears in the run log with the
   reason. MathWorks options are not changed after seeing a result.
5. "Diagnostic" items are reported but have no budget and do not decide the verdict.
6. A scored item that cannot be evaluated (a tool refuses or fails on it) is reported as not evaluable, never
   as agreement, and the verdict does not pass.
7. MathWorks sample data is not used or redistributed. All data is generated by the scripts from the
   repository's own waveform generator and the synthetic PA of `tests/fixtures/synthetic.py`.

## What this can and cannot show

* With the conventions below identical, both estimators solve the same overdetermined least-squares problem.
  Agreement on the registered cases means the basis (index order, lag, degree), the gain scaling, the row
  selection and the way the coefficients are applied are the same in the two tools, in the conditioning range of
  the registered cases. A disagreement means a convention differs or one implementation has a defect.
* It does **not** show that a memory polynomial is a good DPD for any particular amplifier, nor anything about
  measured data: the amplifier here is a synthetic memory polynomial.
* It does not cover rank-deficient or very ill-conditioned bases. The unscaled basis of the registered cases has
  a condition number between about 4·10³ and 3·10⁵ (read from a Python-only exploration before registration,
  see Data); a degree-9 case (about 3·10⁶ to 1·10⁷) was left out on purpose. OpenDPD's optional `rcond`
  truncation has no counterpart in `comm.DPDCoefficientEstimator`.
* The OpenDPD side of the scored items calls the compute-core functions that the run service calls
  (`opendpd.core.polynomial.mp_basis`, `fit_least_squares`, `PolynomialModel`) on double-precision arrays.
  What the run machinery adds (float32 dataset storage, the gain taken from the train split, the zero-filled
  rows at every segment start) is quantified by the diagnostics and by the product-path item Q6, not hidden.
* Not compared, with the reason: **cross-term memory polynomial** and **OpenDPD's GMP** — the bases differ
  (a full cross-term within the memory window against lagging and leading envelope terms with their own
  ranges), so there is no one-to-one comparison; **recursive least squares** — OpenDPD has no RLS fit;
  **MATLAB code generation, `single` precision, fixed-point**; **every non-polynomial OpenDPD model** (the GRU
  family has no `comm.*` counterpart); **`rf.PAmemory`** — mapping a fitted PA model onto it belongs to the
  export work and is verified there.

## Conventions, as read from the installed MATLAB code (R2026a Update 5)

These are statements about the code in `toolbox/comm/comm/+comm/DPDCoefficientEstimator.m`, `DPD.m` and
`+internal/+dpd/dpdcore.m`, not about the published documentation (which is not installed here and was not
consulted). They are the definitions this comparison uses.

| topic | MathWorks | OpenDPD `mp_ls` |
|---|---|---|
| model | `Coef(i,d)` multiplies `x(n-(i-1)) · abs(x(n-(i-1)))^(d-1)`, `Coef` is `MemoryDepth × Degree` | `w[k·Q+q]` multiplies `x(n-q) · abs(x(n-q))^k`, `k = 0…K-1`, `q = 0…Q-1` |
| layout | `Coef(:)` (column-major) lists lag fastest, then degree | `w` lists lag fastest, then degree: the same order, so `Coef = reshape(w, Q, K)` and `Degree = K`, `MemoryDepth = Q` |
| learning | `PA_input ≈ Φ(PA_output / g) · Coef` is fitted, `Coef` is then used as the predistorter (indirect learning) | `x ≈ Φ(y / G) · w` is fitted on the measured train split and copied (indirect learning) |
| gain | `PA_output` is divided by `10^(DesiredAmplitudeGaindB/10)` | `y` is divided by `G = max(abs(y)) / max(abs(x))` (`set_target_gain`) |
| rows | only rows with a complete memory (`n ≥ MemoryDepth`) | delays are zero-filled and reset at every segment start (`nperseg`), so the first `Q-1` rows of each segment are included |
| solver | `xVec \ target` (QR with column pivoting, no column scaling) | column-normalised SVD least squares (`numpy.linalg.lstsq`), cutoff `rcond`, 0 = machine precision |
| application | zero initial delay state; output sample `n` uses `x(n)…x(n-MemoryDepth+1)` | zero-filled delays at the start of a segment |

Consequences the comparison uses: `DesiredAmplitudeGaindB` is set to `10·log10(G)` so that the two divisors are
equal (the property name reads like an amplitude in dB, but the code divides by `10^(g/10)`; diagnostic D3
shows what the other reading would do); the MATLAB estimator is compared with an OpenDPD fit restricted to the
rows with complete memory, and the zero-filled rows are evaluated separately (D2, D4).

## Data

The signals of the LTE registration (`docs/performance/matlab-parity.md`, Signals), generated by the same
code: waveform `ofdm-lte20-v1`, seed 1, 10 subframes, interpolated ×4 to 122.88 MS/s (1 228 800 samples); `x` is
the PA input `a · x_4` and `y = memory_polynomial_pa(x)` the PA output, in double precision (not rounded to
float32 unless stated), with `a = 0.35` (**S4**) and `a = 0.50` (**S5**). `G = max(abs(y)) / max(abs(x))` over the whole
record: 0.5674 (S4) and 0.4030 (S5). Both sides receive identical arrays.

Four cases, each a (record, `K`, `Q`) combination:

| case | record | Degree `K` | MemoryDepth `Q` | unscaled condition number of the basis |
|---|---|---|---|---|
| C1 | S4 | 5 (MathWorks default) | 3 (MathWorks default) | 4.3·10³ |
| C2 | S4 | 7 | 5 | 1.4·10⁵ |
| C3 | S5 | 5 | 3 | 6.7·10³ |
| C4 | S5 | 7 | 5 | 3.1·10⁵ |

The condition numbers (2-norm, basis rows with complete memory, `y/G`) were computed in Python before this
registration to choose cases whose conditioning is moderate, so that the budgets below test the conventions
and not the arithmetic; no estimator of either tool had been run on this data at that time.

**Constructed exact problem.** For every case, `c_true[k,q] = 0.6^(k+q) · (−1)^k · exp(j(0.35(k+1) + 0.6(q+1)))`
(`k = 0…K-1`, `q = 0…Q-1`, a deliberately asymmetric set so that a transposed or reordered layout cannot
agree by accident). With `v = y/G`, the constructed input is `x_syn[n] = Σ c_true[k,q] · v[n-q] · abs(v[n-q])^k`,
zero before the start of the record, computed in NumPy by a direct double loop in the harness, independently of
`mp_basis`. The fit of `x_syn` from `y` has zero residual, so a correct estimator recovers `c_true` up to the
conditioning, with no residual-dependent term.

## MathWorks configuration

## Amendment 1 (2026-10-09, before run 1)

The registration of Q6 says that an `mp_ls` PA run and an `mp_ls` DPD run are trained. The service refuses a
least-squares baseline as the PA reference of a DPD run ("a PA-modeling reference, not a DPD surrogate"), which a
plumbing check on truncated data (60 000 samples per record, not the registered data, no report written) showed
before any registered run. The harness therefore trains a small gradient-trained GRU surrogate (`hidden_size` 6, one
epoch, CPU) as the DPD run's PA reference; the DPD run is the `mp_ls` run with `K = 5`, `Q = 3` as registered. The
platform identifies the postdistorter on measured data and uses the surrogate only for evaluation, so the
surrogate does not enter the coefficients that Q6 and D4 compare. No item, budget or case changes.

## Results

**Verdict: the registered memory-polynomial parity passes** — 21 of 21 scored items are within budget, with
margins of several orders of magnitude (the largest scored difference relative to its budget is Q5, 2.5·10⁻⁸
against 1·10⁻⁶, which is the float32 interface). Run on MATLAB R2026a Update 5 (Communications Toolbox 26.1),
Linux. The working tree had uncommitted changes in documentation files under `Matlab/toolbox` only; no code
under test, no script and no `.m` file was modified.

What the scored items show:

* **The two tools define the same polynomial.** `comm.DPD` with the true coefficients reproduces the
  independently constructed input to 6·10⁻¹⁶ relative (Q3), in all four cases.
* **Both estimators recover a known answer in the same layout.** From the constructed exact problem the MathWorks
  estimator returns `c_true` with relative error at most 4.7·10⁻¹³ (Q1) and OpenDPD's fit at most 8.9·10⁻¹⁴
  (Q2), including the cases whose unscaled condition number is 1.4·10⁵ and 3.1·10⁵. The layout is
  `Coef = reshape(w, Q, K)` with `Degree = K` and `MemoryDepth = Q`; an asymmetric `c_true` rules out a
  transposed or reordered layout agreeing by accident.
* **On the plant data they give the same predistorter.** With the complete-memory rows and
  `DesiredAmplitudeGaindB = 10·log10(G)`, the coefficient vectors agree to at most 3.9·10⁻¹³ (D1) and the
  predistorter outputs to at most 4.8·10⁻¹³ relative (Q4).
* **`comm.DPD` can run OpenDPD's coefficients.** Through the `PolynomialModel` module's float32 interface the
  outputs differ by 2.5·10⁻⁸ relative (Q5), which is float32 rounding.
* **The run service stores what the compute core computes.** The coefficients in the checkpoint of the SDK-trained
  `mp_ls` DPD run are identical to the fit recomputed from the run's stored train split (Q6: difference 0).

What the diagnostics add (no budget, so no verdict, but they are the practical content for a MATLAB user):

* **The gain setting must be `10·log10(G)`.** Reading `DesiredAmplitudeGaindB` as `20·log10(G)` (D3) gives
  coefficients that differ from OpenDPD's by 83 % to 97 %. The estimator divides `PA_output` by
  `10^(DesiredAmplitudeGaindB/10)`; to reproduce OpenDPD's `G = max|y| / max|x|` the property is `10·log10(G)`.
* **An OpenDPD run and the MathWorks estimator differ by the zero-filled rows, and by nothing else we could
  find.** OpenDPD includes the first `Q-1` rows of every `nperseg` segment, with delays filled by zeros, because
  the model is evaluated with exactly that state reset; MathWorks uses only rows with complete memory (D2). With
  `nperseg` = 2048 the coefficient vectors differ by 0.6 % and 0.9 % for `K = 5`, `Q = 3`, and by 11 % and 19 %
  for `K = 7`, `Q = 5`, where the basis is worse conditioned; the predistorter outputs on the same signal differ
  by 0.12 % to 0.70 % relative (0.03 % to 0.54 % when the segmented coefficients are applied continuously). The
  residual of the segmented fit on the complete-memory rows is at most 0.11 dB worse than that of the
  complete-memory fit (below 0.01 dB for `K = 5`, `Q = 3` on S5). Through the product path (D4, `K = 5`, `Q = 3`) the MathWorks estimator differs from the checkpoint by
  0.624 %, and the segmented fit differs from the complete-memory fit by 0.623 % on the same split: the difference
  is accounted for by the zero-filled rows.

Limits of this evidence:

* One MATLAB release on one platform; a synthetic memory-polynomial amplifier; degrees up to 7 and memory depths
  up to 5, in a conditioning range of about 4·10³ to 3·10⁵. Nothing here says how the two behave on a rank-deficient
  or much worse conditioned basis, where OpenDPD's column scaling and `rcond` cutoff and MathWorks' unscaled QR
  solve would be expected to diverge.
* The scored items of the OpenDPD side call the compute-core functions the run service calls. Q6 ties them to one
  SDK-trained run; it does not test every model configuration the service accepts.
* Only the memory polynomial is compared. OpenDPD's GMP and the cross-term memory polynomial of MathWorks have
  different bases; the GRU family has no `comm.*` counterpart.

What this run does **not** do: it does not change how `mp_ls` is fitted. Whether to offer a complete-memory-rows
option for MATLAB-comparable coefficients is a decision for the maintainers; it would not change the frozen
Arena baselines, which are fitted as they are.
