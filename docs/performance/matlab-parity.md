# OpenDPD ↔ MATLAB parity

Status: **pre-registered; run 1 done, amendment 1 registered, run 2 pending** (2026-10-08). The registration (rules, signals, procedures, budgets and
the scored/diagnostic split) was committed before any comparison script existed or was run. The commits that
follow change only this status line, the run log and the Results section; they do not edit the registration. If
the registration itself must change, that is a dated amendment appended below, never an edit in place.

OpenDPD's EVM and ACLR numbers are only as useful to MATLAB users as they are checkable against the tools they
already trust. This document fixes **what is compared, with which MathWorks functions and which error budgets,
before any number exists**, and records the outcome afterwards, including everything that does not agree.

## Rules

1. Signals, MathWorks configuration and budgets below are fixed before the first run. A run never changes them.
2. Budgets for the LTE cross-validation (P2, P3) are those of `docs/protocols/waveform-profiles.md` §5, which
   were fixed there "before any model comparison, never relaxed afterwards": adjacent-channel ratio within
   **0.1 dB**, RMS EVM within **0.05 percentage points**. They are not re-derived here.
3. An item passes if its measured difference is within its budget. An item outside its budget is reported as
   failed with the numbers; the explanation is a hypothesis until it is shown (a diagnostic run is allowed and
   is reported next to the failure, never instead of it).
4. If a comparison disagrees because the **MATLAB-side code does not implement the registered procedure** (a
   bug in the check, not a difference between the two tools), the MATLAB code is corrected to the registered
   procedure and the run is repeated. Every run, including the ones discarded, appears in the run log with the
   reason. MathWorks options (windows, segment lengths, filters) are not changed after seeing a result.
5. "Diagnostic" items are reported but have no budget and do not decide the verdict.
6. MathWorks sample data is not used or redistributed. Every signal is generated by the scripts from the
   repository's own waveform generator and the synthetic PA of `tests/fixtures/synthetic.py`; MATLAB needs only
   its own licensed toolboxes.

## What this can and cannot show

* It checks OpenDPD's implementation of the procedure documented in `docs/protocols/waveform-profiles.md` §2
  against an **independent implementation of the same documented procedure** written with MathWorks building
  blocks (`lteOFDMModulate`, `lteOFDMDemodulate`, `lteEVM`, `resample`, `comm.ACPR`), and the ACLR against
  `comm.ACPR` used as MathWorks documents it. A disagreement means one implementation has a defect or the two
  tools define the quantity differently; agreement means neither has a defect that the registered signals can
  expose.
* It does **not** show that the profile equals 3GPP TS 36.104 Annex E. The deviations listed in the protocol
  (§2, "Deviations from a standard EVM procedure") remain; quantifying them against a standards-conformant
  EVM measurement is a separate step.
* Not compared, with the reason: **5G NR EVM** — OpenDPD has no NR waveform profile, so there is nothing to
  compare to the 5G Toolbox; adding one is a protocol decision, not a MATLAB-compatibility task. **Hardware**
  — nothing here is measured. **Other MATLAB releases** — one release is recorded (below).

## Environment (recorded with the results)

MATLAB release and update, the version of every toolbox used (LTE Toolbox, Communications Toolbox, Signal
Processing Toolbox), Python, NumPy, SciPy, the OpenDPD commit, and the SHA-256 of every input signal and script.

## Signals

All generated deterministically by one script and stored as float32 I/Q, the precision of OpenDPD datasets;
both sides read the same stored values and convert to double.

Waveform: `ofdm-lte20-v1`, seed 1, 10 subframes (`opendpd waveforms generate --seed 1 --subframes 10`): 307 200
samples at 30.72 MS/s. Interpolation to a higher rate `U` is band-limited and exact for this periodic signal
(FFT zero padding). The PA is `memory_polynomial_pa` of `tests/fixtures/synthetic.py`, applied to
`a · x_U` where `a` is the drive scale. The four drive levels were chosen to span about 1 % to 11 % EVM and
−41 to −27 dBc ACLR; this was read from a Python-only exploration before any MATLAB comparison existed, for
coverage and not to favour any outcome.

Welch segment length `nperseg` for the ACLR: 1024, 2048, 4096 for the 122.88 MS/s signals (resolution bandwidth

(±9, ±11, ±29 MHz) falls on a bin boundary or centre in the same way for both tools.

## P1 — waveform generation

LTE Toolbox `lteOFDMModulate` (`NDLRB = 100`, normal cyclic prefix, windowing 0) applied to the package's
`symbols.npy` (placed on the 1200 grid rows k = −600…−1, +1…+600 of 140 symbols) against the package waveform
`x.npy`. Compared after the single real scale factor that minimises the difference (reported).

| item | budget | kind |
|---|---|---|
| same sample count and same first-sample alignment | exact | scored |
| relative RMS difference ‖x − s·x_ref‖ / ‖x‖ | ≤ 1·10⁻⁶ | scored |
| scale factor s | reported | diagnostic |

The budget is set by the float32 storage of the package (about 6·10⁻⁸ relative) with an order of magnitude of
margin.

## P2 — ACLR against `comm.ACPR`

Signals S2–S8 (S1 and S9 are diagnostic: an ideal signal's adjacent power is below the estimator floor, which the
protocol says is "reported with the floor stated, not scored"). For every signal and every `nperseg`, the OpenDPD value is
`ofdm-lte20-evm-v1` `ACLR_L` and `ACLR_R` (main channel [−9, +9] MHz, adjacent channels centred at ∓20 MHz, 18 MHz
rectangular bandwidth, Welch with Hann, 50 % overlap). The MATLAB value is `comm.ACPR` with
`MainChannelFrequency = 0`, `MainMeasurementBandwidth = 18e6`, `AdjacentChannelOffset = [-20e6 20e6]`,
`AdjacentMeasurementBandwidth = 18e6`, `SampleRate = fs`, `PowerUnits = 'dBW'`, in two registered modes:

* **MathWorks default** (`SpectralEstimation = 'Auto'`: Welch, Hamming, no overlap, one segment spanning the
  input, i.e. the finest resolution the capture allows). This is the "toolbox function with its default
  procedure" of protocol §6.2. It does not depend on `nperseg`, so it is evaluated once per signal and compared
  with each `nperseg` of OpenDPD.
* **Aligned** (`SpectralEstimation = 'Specify window parameters'`, `SegmentLength = nperseg`,
  `OverlapPercentage = 50`, `Window = 'Hann'`, `FFTLength = 'Same as segment length'`), the same estimator
  settings as OpenDPD.

Left is the channel at −20 MHz, right at +20 MHz; the sign convention is leakage in dBc (negative), as in OpenDPD.
The MATLAB script first checks the sign and unit of `comm.ACPR` on a signal of known ratio and stops if they
differ from this convention.

| item | budget | kind |
|---|---|---|
| \|ACLR_OpenDPD − ACLR_ACPR(default)\| per signal, side, `nperseg` | ≤ 0.1 dB | scored |
| \|ACLR_OpenDPD − ACLR_ACPR(aligned)\| per signal, side, `nperseg` | ≤ 0.1 dB | scored |
| the same for S1 and S9 | reported | diagnostic |
| a third comparator, SPT `pwelch` with the OpenDPD settings and band rule | reported | diagnostic |

## P3 — EVM against an independent implementation with MathWorks building blocks

Signals S0–S9. OpenDPD value: `ofdm-lte20-evm-v1` `EVM_RMS` (percent). The MATLAB value is produced by this
chain, written from the procedure of protocol §2 and not from OpenDPD's code:

1. Rate conversion to 30.72 MS/s by `resample(y, p, q)` (MathWorks default Kaiser filter) with the exact rational
   `p/q = 30.72e6/fs`.
2. Reference waveform `x_ref = lteOFDMModulate` of the package symbols (as P1). Integer timing τ from the circular
   cross-correlation magnitude (FFT based) of the first `period` samples with `x_ref`; same sign convention as
   OpenDPD, y[n] ≈ x[(n + τ) mod period]. The registered signals have τ a whole number of subframes (0, or
   3 × 30 720 for S6 and S9), so every OFDM symbol of the capture is complete; the handling of symbols cut by the capture edge
   is covered by the repository's unit tests, not by this comparison.
3. Coarse carrier frequency offset: the cyclic-prefix correlation of every symbol, skipping the first 32 prefix
   samples; f = −angle(Σ head·conj(tail)) / 2π × 15 kHz.
4. Up to three rounds of: correct the offset, `lteOFDMDemodulate(enb, ·, 1)` (FFT at the end of the cyclic
   prefix), one least-squares complex gain per subcarrier from the known symbols over all symbols
   (H = Σ conj(S)·Y / Σ |S|²), equalise, then the fine offset from the slope (`polyfit`) of the unwrapped per-symbol
   residual phase against time, stopping when the update is below 1 mHz. No per-symbol phase tracking.
5. `evm = lteEVM(S_equalised(:), S_reference(:))`; `EVM_RMS = 100 · evm.RMS`.

| item | budget | kind |
|---|---|---|
| \|EVM_OpenDPD − EVM_MATLAB\| per signal | ≤ 0.05 percentage points | scored |
| integer timing τ equal (S6, S9; τ = 0 for the others) | exact | scored |
| carrier frequency offset on S9: each tool within 0.01 Hz of the injected +350 Hz | ≤ 0.01 Hz | scored (protocol §5) |
| carrier frequency offset on S6: difference between the two estimates | reported | diagnostic |
| the same chain fed with OpenDPD's own rate-converted baseband signal (isolates the two resamplers) | reported | diagnostic |
| `lteFrequencyOffset` coarse estimate on S6 | reported | diagnostic |
| rate-conversion difference: ‖`resample` − `resample_poly`‖ / ‖·‖ per rate | reported | diagnostic |

The protocol records a 0.037 % EVM floor after rate conversion from 122.88 or 800 MS/s. A resampler difference
of that size is within the 0.05 point budget only when it adds in quadrature to a larger EVM; the diagnostic row
makes the contribution visible rather than assumed.

## P4 — verdict rule

The LTE cross-validation (protocol §6) **passes** only if every scored item of P1, P2 (both modes) and P3 is within
its budget. A partial result is reported as such, item by item. The `validation` flag of
`opendpd/core/metrics/ofdm_evm_v1.py` is a protected-path change that needs science review; this document
supplies evidence for that review and does not change the flag.

## Amendment 1 (2026-10-08, after run 1 and before run 2)

Run 1 showed two things the registration did not anticipate. Nothing registered above is changed; this amendment
only adds items, and it is committed before the harness gains them.

**F1 — timing range.** The timing step (protocol §2 step 2) is a circular cross-correlation without
frequency-offset compensation, so with the 10-subframe package (T = 10 ms) its normalised peak falls as
|sinc(f·T)| with the carrier offset f. Measured with OpenDPD alone, before any MATLAB comparison of these
signals: 0.98 at 10 Hz, 0.86 at 30 Hz, 0.64 at 50 Hz, 0.009 at 100 Hz, 0.09 at 350 Hz; with a 1 ms waveform
(which the repository's ±350 Hz unit test uses) 0.81 at 350 Hz. Below 0.3 the profile reports
`missing_reference`. S6 and S9 (+350 Hz) are therefore refused by both OpenDPD and the MATLAB chain (peak
0.090 in both), so their scored EVM, timing and frequency-offset items have no value to compare.

**F2 — band integration.** The registration assumed that the band edges fall on bin boundaries or centres "in the
same way for both tools". They do not: ±9 MHz are bin centres at the registered resolutions, but ±11 and ±29 MHz
fall 1/3 of a bin from a centre (183.33 and 483.33 bins at 60 kHz), and the two tools treat such edges
differently. OpenDPD sums the bins whose centre lies in [lo, hi); `comm.ACPR` sums the enclosing range (the last
bin at or below lo through the first bin at or above hi), which at 60 kHz is 302 bins in each adjacent channel
against OpenDPD's 300, and 301 against 300 in the main channel. Run 1 reports 7 ACLR values outside the 0.1 dB
budget (all on S2, S3; the largest 0.21 dB).
